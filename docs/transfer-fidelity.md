# Transfer fidelity: where the local surrogate and AWS AgentCore Policy differ

A ledger. Each entry: the field or construct, what our local pipeline does, what AWS documents (with a source),
and whether a local result on it transfers to AgentCore. "Local" means cedar-policy-mcp-schema-generator 0.7.0
with the generator defaults in `pgi.schemagen.CONFIG` (`numbersAsDecimal: False`, `objectsAsRecords: False`),
plus our generators and oracle; for the temporal track, "local" is Dogwood's own generator (`pgi.schemagen.DOGWOOD_PROFILE`:
outputs on, numbers as decimal) and the Dogwood reference interpreter 1.1.0 with its default event schema. AWS's generator settings are not published; the AWS column is what its
documentation states. An entry's "transfers" column is about the schema and the decision, not about whether an
LLM behaves the same on both sides.

| # | Field / construct | Local behaviour (verified) | AWS behaviour (documented) | Transfers? |
|---|---|---|---|---|
| 1 | JSON Schema `number` | Becomes the opaque entity type `AOB::Number` (no attributes, identity only). A policy cannot compare, bound or order it; `3` and `3.0` are different entity ids. Verified on `close_workorder.actual_hours` (docs/findings.md, Step 2 table). | Becomes Cedar `Decimal`: "Decimal is an extension type in Cedar, which does not exactly match IEEE floating point numbers, so numbers will be truncated to the Cedar representation." Conditions use `.lessThan()`, `.greaterThan()` etc. against `decimal("…")` literals with at most 4 decimal places. Source: [Schema constraints, Context table](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-schema-constraints.html). | **No** for any numeric condition. Locally a generator cannot write a bound on hours and the oracle cannot judge one; on AWS it can. Local "no policy can bound hours" is an artefact of `numbersAsDecimal: False`, not a property of AgentCore. Re-run numeric scenarios with `numbersAsDecimal: True` before claiming anything about AWS. |
| 2 | `$ref` / `$defs` in `inputSchema` | Not ignored. 0.7.0 resolves an internal reference: `site_id: {"$ref": "#/$defs/Site"}` with `$defs.Site = {type: string, enum: [MAIN]}` yields `site_id: AOB::close_workorder::Input::Site` and `entity Site enum ["MAIN"]`; an unused `$defs` entry still emits `type Site = String;`. A dangling `$ref` fails generation with `SchemaGeneratorError: Error adding tools: Undefined Reference Type` (checked 2026-11-15 on scratch copies; the pinned `outputSchema`s carry `$defs` but outputs are not read with `includeOutputs: False`). | The Gateway rejected tool schemas with references at target registration: `"Invalid tool schema, $ref is not supported"` ([awslabs/mcp#2442](https://github.com/awslabs/mcp/issues/2442), Pydantic-generated `$defs`/`$ref`). With MCP protocol version 2026-07-28, AWS states input schemas "gain composition keywords (oneOf, anyOf, allOf), conditionals, and internal references ($ref, $defs)" ([How AgentCore Gateway supports the MCP 2026-07-28 spec](https://aws.amazon.com/blogs/machine-learning/how-agentcore-gateway-supports-the-mcp-2026-07-28-spec/)). How Policy's Cedar schema generation treats them under either version is not documented. | **No.** Behaviour differs by protocol version and is undocumented for Policy. Our mutators never introduce `$ref`/`$defs` (`pgi.mutators.edit`), and no manifest containing them is to be sent to AWS. |

| 3 | Tool `outputSchema` (temporal track) | Emitted: each tool action's context gains `output?: <tool>Output`, and a `::response` predicate can bind `output.<field>` (verified on `wo.dogwood.generated.cedarschema`; Cedar-track pin has no `output`). Union outputs (`anyOf` in `$defs`) become `result: {typeChoice0?: <entity>, typeChoice1?: <entity>}`: a policy can test which branch fired (`output.result.typeChoice0: _`) but cannot read fields inside the entity. | "`output.<name>`: An output field of the action. Available on `response` events only." Response events "carry the action's input and output fields". Example predicates bind `output.approved: true` and `output.claimId`. Source: [Authoring temporal policies, Event schema](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal-authoring.html). | **Yes** for flat output fields. Union/nested outputs: AWS's encoding of `anyOf` outputs is undocumented, so a result that depends on the opaque-union behaviour is local only. |
| 4 | JSON Schema `number` (temporal track) | `decimal` (`actual_hours?: decimal`, `hours_planned?: decimal`), because Dogwood's generator fixes `encode_numbers_as_decimal(true)`. Entry 1's `AOB::Number` opacity does not apply here. | Cedar `Decimal` (entry 1). | **Yes** for the type; Dogwood's temporal comparisons treat decimals as equality-only (interpreter docs, 04-temporal-expressions), which AWS does not document either way. |
| 5 | Temporal event schema: pin and field names | **Reference scenarios use our AWS-shaped `domains/assetopsbench/schema/agentcore.dwschema`** (`event_schema=` on every oracle call): `pin sessionId = context.sessionId` on request/response/error, `eventPrincipal`/`eventResource` unpinned, `eventResource: resource` written in every predicate, `sessionId: String` declared on every action by `pgi.schemagen.link_session_id`. Verified: session boundary enforced; another principal's evidence in the same session counts (tests/test_temporal_scenarios.py). Dogwood's *default* schema differs (universal `callerPrincipal` pin, fields `callerPrincipal`/`callerResource`); kept only for the `gold.principal-pin.dw` variant. Deltas vs AWS that remain: Dogwood's validator does not enforce the `eventResource: resource` requirement (we do it by hand and could lint it); our `request_context` must carry `sessionId` explicitly, where AWS reads the `x-amzn-bedrock-agentcore-policy-session-id` header. | `request`/`response`/`error`, each with `eventPrincipal: principalType(A)`, `eventResource: resourceType(A)`, `requestId`, `pin sessionId: String = context.sessionId`. "Temporal history is scoped to the session"; "every temporal predicate must include" `eventResource: resource`. Source: [Authoring temporal policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal-authoring.html), [Temporal policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal.html). | **Yes** for the pin and field names under `agentcore.dwschema` (decided 2026-11-16). A policy missing `eventResource: resource` validates locally but AWS documents it as required: flag it before sending anything to AWS. |
| 6 | Action and event naming / recording | `Drupe::Action::"<tool>"`, template principal `Drupe::User`, resource `Drupe::Gateway`. The reference interpreter records whatever the trace says; an `error` event is written by the trace author. Window cap 24h (default `max_window`). | `AgentCore::Action::"<Target>___<tool>"`, resource `AgentCore::Gateway::"<arn>"`. "A permitted action that completes is recorded as a `response` event, and an action that a policy denies is recorded as an `error` event", so a prerequisite action needs its own plain permit. Quotas: 20 temporal policies per engine, 3 temporal operators per policy, 24h maximum window. Source: [Temporal policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal.html). | **Yes** for decisions once names are mapped; the operator and window quotas must be respected by any policy meant for AWS. The "denied → error, never response" recording rule is a trace-authoring rule locally. |

| 7 | Interpreter version skew (temporal track) | `pydogwood` 0.1.1 wheel → crates.io `dogwood-language` **1.1.0** (`pydogwood.DOGWOOD_VERSION`). Upstream `dogwood-policy/dogwood` `main` at `929f49e` (2026-11-12) is **1.1.2**. CHANGELOG 1.1.0→1.1.2: parse/lowering limits (depth 32, 1,000,000-node budgets, >32-term chains rejected), i64-range literal checks, `//` comments inside `temporal {}` now inert, `def temporal` macro hygiene; no change listed to verdict semantics, replay JSON, or `schema mcp` defaults. Same discipline as the cedarpy 4.12.0 / Cedar CLI 4.14.1 skew (decisions 2026-11-12). | AWS does not publish which Dogwood version its policy engine runs. | **Unknown version on AWS.** If a local verdict ever depends on something the changelog names (deep nesting, long chains, comments in temporal blocks, macros), re-run against a CLI built at `929f49e` before transferring; otherwise treat 1.1.0 ≡ 1.1.2 for the constructs the t01 policies use. |

| 8 | Natural-language generator prompt (temporal track) | Our surrogate generators get a static, scenario-free Dogwood language reference (`pgi.generators.dogwood.LANGUAGE_REFERENCE`, transcribed from the AWS authoring/examples pages and the Dogwood guide, 2026-11-16), the outputs-on action schema, the AWS-shaped event schema and the raw manifests; the intent is the user turn. | AWS: "You can also create a temporal policy by describing it in natural language"; the prompt, the language material and the schema profile it uses are not published. Source: [Authoring temporal policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal-authoring.html). | **Unknown.** Clean reconstruction rates measured locally are evidence about the pattern (an LLM compiling intent + manifests into Dogwood), not about AgentCore's generator; the AWS arm must be run with AgentCore's own generator. |

## How to add an entry

Verify the local column on a scratch copy (never a pinned file) and quote the AWS column from a primary source
with a link. If a surrogate result depends on an entry marked "No", say so where the result is reported.
